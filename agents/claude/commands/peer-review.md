---
description: チームメンバーの変更をreviewerエージェントでピアレビューし、指摘内容を整理。振り返りもやる。
argument-hint: [レビュー対象] [reviewer名]
---

以下の手順を順番に実行してください。

## ステップ1: 引数の解釈

$ARGUMENTS を以下のルールで解釈してください：
- 第一引数: レビュー対象（省略時は `diff` = 現在のunstaged changes + untracked files）
- 第二引数: reviewer名（省略時は全reviewerを並列実行）

### レビュー対象の指定方法
- 指定なし / `diff`: `git diff` + `git ls-files --others --exclude-standard` で新規ファイルも取得
- `staged`: `git diff --cached`
- `branch` または `ブランチ`: `git diff origin/main...HEAD`
- `PR #123` / `pr 123` / PR の URL: ステップ2で取得した差分
- その他: そのまま渡す

### 利用可能なreviewer名
- `reviewer` - Claude自身による設計と実装のレビュー
- `nonfunctional-reviewer` - Claude自身によるセキュリティと非機能（性能、資源の使用効率、障害時の挙動）のレビュー
- `codex-reviewer` - Codex CLIを使ったレビュー

reviewer名が上記のいずれにも一致しない場合は、エラーとしてユーザーに利用可能なreviewer名を案内してください。

## ステップ2: レビュー対象の最新化

2回目以降のレビューの可能性があります。レビュー対象がPRなら、次の手順でHEADを取得します。

- `gh pr view` で base ブランチ（`baseRefName`）、本文、関連 Issue を確認する。base は main とは限らない
- base と PR の HEAD を `origin/<base>` と `origin/pr-<番号>` に fetch する。作業ツリーの切り替えや worktree の作成はしない
- 差分は `git diff origin/<base>...origin/pr-<番号>` で読む

## ステップ3: レビュー実行

- reviewer名が指定された場合: そのreviewerのエージェントを起動する
- reviewer名が省略された場合: 全reviewerのエージェントを同時に並列起動する

各reviewerへの依頼には、次を渡します。

- レビュー対象の範囲（ステップ2の base と head、または差分の取り方）
- 作者の意図（PR 本文、Issue）
- 尊重すべきドキュメントの場所（README.md, CLAUDE.md, AGENTS.md, docs/ など）

依頼文で細部の観点を列挙しません。reviewer の注意が列挙した観点に寄り、設計の評価が抜けるためです。

## ステップ4: レビュー結果統合

すべてのレビューが完了したら、結果を統合し、下のフォーマットでユーザーに示します。コードは変更してはならない。

- 設計の指摘と実装の指摘を分け、設計を先に示す
- 実装の指摘は MUST / SHOULD / NITS / NO_NEED に分類する
- 設計の指摘が通れば不要になる実装の指摘は、対応方針の欄にそう書く
- 件数は `n / 起動したreviewer数`
- 該当の無い節は省く

```markdown
# <対象> レビュー結果

- reviewer: <起動した reviewer>
- 統合者が確かめた範囲: <コードで裏取りした指摘の番号。残りは reviewer の報告のまま>

## 結論
<1〜3 文>

## 設計の指摘
| # | 指摘 | 指摘元 | 件数 | 対応方針 |
| --- | --- | --- | --- | --- |

## 実装の指摘

### MUST
| # | 指摘 | 場所 | 指摘元 | 件数 | 対応方針 |
| --- | --- | --- | --- | --- | --- |

### SHOULD
| # | 指摘 | 場所 | 指摘元 | 件数 | 対応方針 |
| --- | --- | --- | --- | --- | --- |

### NITS
- <指摘>（<指摘元>、<件数>）

### NO_NEED
- <指摘>（<理由>）

## 問題なしと確かめた点
- <reviewer が確かめた面>（<指摘元>）

## 決めてほしい点
1. <ユーザーの判断が要る点>
```

レビューすべき内容について、ユーザーとディスカッションしながら整理します。

## ステップ5: レビュー結果報告

ユーザーが実施します。

## ステップ6: 振り返り

ユーザーが実際に報告した指摘と、統合結果を比べます。ユーザーが挙げたのに reviewer が挙げなかった観点と、統合結果で重く扱ったのにユーザーが採らなかった指摘を整理し、このコマンド、reviewer の定義、リポジトリ内のドキュメントやCLAUDE.md、AGENTS.mdの改善が行えないか検討します。
