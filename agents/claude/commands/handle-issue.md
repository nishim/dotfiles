description: GitHub Issueの対応実施
argument-hint: [issue-id] [root-branch]
---

以下の手順を順番に実行してください。

## ステップ0: Worktree 作成

### 0-1: 元となる ブランチの準備

EnterWorktree は HEAD ベースで worktree を作成するため、事前に main かつ最新であることを保証します。
ただし、ユーザーが root-branch を指定した場合はmainではなくそちらにしたがってください。

```bash
git switch main
git pull origin main
```

もし main 以外のブランチにいて switch できない場合（未コミットの変更がある等）は、ユーザーに確認してから進めてください。

### 0-2: Worktree 作成

`EnterWorktree` ツールで worktree を作成し、隔離された作業環境に入ります。
worktreeもブランチ名も**必ず** `issue-${issue-id}` (例: issue-42) とします。

### 0-3: 依存関係セットアップ

プロジェクトの手順に従って依存関係をインストールします。

```bash
# 例: pnpm プロジェクトの場合
pnpm install --frozen-lockfile
```

## ステップ1: issueに担当者をアサイン

issueの担当者を明確にするため、私を担当者としてアサインしてください。
すでに私以外の担当者がいる場合は、判断を仰いでください。

## ステップ2: デザイン

issueの内容、コードベース、 @docs にある仕様を理解し

- どう実装するか
- なぜその意思決定をしたか

をまとめます。

実装の目的や要件の解釈が実質的に分かれる場合のみ、AskUserQuestion で確認します。
命名・同等な実装方式の選択などの軽微な判断は自分で決め、その旨をデザインに記録します。
確認結果はissueやissueコメントとしてフィードバックします。

## ステップ3: 実装

必要な回数、3-1, 3-2を繰り返します。

もし複数PRを作成する場合は、ブランチ名は `issue-${issue-id}/{topic}` とします。

### ステップ3-1: テスト実装

テストファーストです。
これから実装する対象のテストを書き、failすることを確認します。

### ステップ3-2: アプリケーションコード・インフラ実装

Issueに書かれたToBeを満たしつつ、

- テスト
- lintやフォーマット
- IaC の検査（例: terraform plan）
- その他プロジェクトで実施すべき検査

をパスするように実装します。
テストに誤りがあれば修正します。

## ステップ4: セルフレビュー

ここまでの作業をcommitし, `/self-review` でセルフレビューと修正を行います。

## ステップ5: PR作成

作業ブランチをpushし、PRを作成します。
PRにはどう動作確認すべきかplaybookを含めてください。
作成後、PRの担当者を明確にするため、私を担当者としてアサインしてください。

PR作成にはユーザー確認は不要です。

## ステップ6: ユーザーレビュー

ユーザーがレビューや質問、PRのマージなどを行います。
ユーザーの指摘によりコード、issue、prの変更が必要な場合は随時実施してください。

ユーザーから明示的な指示がない場合は、このステップを継続します。

## ステップ7: 作業完了・Worktree 退出

`ExitWorktree` ツール (action: `remove`) で元のディレクトリに戻ります。
