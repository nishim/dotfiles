# prompt-migrate — プロンプト資産のモデル追従アップデート

agent / skill / command / CLAUDE.md / AGENTS.md といったプロンプト資産を、最新の prompting best practices とモデル固有の挙動差分に照らしてレビューし、必要な箇所だけを更新する。

原則: **盲目的な自動上書きをしない**。スコープ確認 → 差分提案 → ユーザー承認 → 編集、の順を必ず守る。

## ステップ1: 対象モデルの確認

どのモデル向けに最適化するかを特定する。

- スラッシュ起動の引数（例: `/prompt-migrate opus5, fable5を前提にプロンプトを更新してください`）や会話でユーザーが明示していれば従う。複数モデル指定なら全対象モデルで問題なく動くことをゴールにする
- 不明なら AskUserQuestion で確認する（例: Opus 5 / Fable 5 / Sonnet 5 / 複数対応）

## ステップ2: 最新ドキュメントの取得

**URL をハードコードした知識に頼らず、毎回 WebFetch で最新を取得する。** 起点は以下の3ページ。ここから対象モデルの固有ページや新設ページへのリンクを辿る（モデルは今後増えるため、リンクの発見的な探索を優先する）:

- prompting best practices（モデル固有ページへのハブを兼ねる）:
  `https://platform.claude.com/docs/ja/build-with-claude/prompt-engineering/claude-prompting-best-practices`
- モデル概要（現行モデルの一覧）:
  `https://platform.claude.com/docs/ja/about-claude/models/overview`
- 移行ガイド（世代間の変更点）:
  `https://platform.claude.com/docs/ja/about-claude/models/migration-guide`

best practices ページの冒頭に各モデル固有ページ（例: `prompting-claude-opus-5`, `prompting-claude-fable-5`）へのリンクがある。ステップ1で決めた対象モデルの固有ページを必ず取得する。リンク切れ・未知のモデル名の場合は、モデル概要ページから該当ページを探す。

## ステップ3: 2種類の情報源を区別する

取得した内容は次の2種類に分けて扱い、レビュー観点・出力ラベルとして最後まで混同しない:

| ラベル | 情報源 | 用途 |
|---|---|---|
| `[BP]` | prompting best practices（普遍的な原則） | 既存プロンプトが原則に沿っているかのレビュー。例: 明確さ、XML構造化、例の使い方、役割付与 |
| `[MODEL]` | モデル固有ページ・移行ガイド（挙動差分） | 旧モデル前提の記述の検出と修正。例: 過剰な強制語（MUST/必ず）、検証指示の要否、冗長性・スコープ・サブエージェント制御、廃止された手法（prefill 等） |

## ステップ4: 対象ファイルのスコープ確認（必須）

候補ファイルを列挙して一覧をユーザーに提示し、**絞り込みの確認を得てから**次に進む。無条件の一括変更は禁止。

探索する場所の例（プロジェクトにより異なる。実際に存在するものだけ挙げる）:

- `.claude/agents/`, `.claude/skills/`, `.claude/commands/`
- `CLAUDE.md`, `AGENTS.md`（ルートおよびサブディレクトリ）
- リポジトリ固有のプロンプト置き場（例: dotfiles の `agents/` 配下、`~/.claude` のソースディレクトリ）

一覧には各ファイルの1行説明を添え、AskUserQuestion で「全部 / 一部 / 指定」を選べるようにする。

## ステップ5: レビューと差分提案

スコープ内の各ファイルを読み、指摘を次の3分類で整理する:

1. **変更提案** — モデル起因で修正すべき箇所。ファイルごとに「何を」「なぜ」（`[BP]` / `[MODEL]` ラベルと根拠になったドキュメント記述）を示す
2. **変更不要** — 問題なしと判断したファイル。ひとことで理由を添える
3. **要対応事項** — プロンプト編集では済まない項目。自動編集せず報告のみに留める（例: API パラメータや呼び出し方法の変更 → `/claude-api migrate` を案内、ツール構成の再設計、評価が必要な大きな書き換え）

**提案一覧をユーザーに提示し、承認を得てから編集する。** 項目単位で取捨選択できる形（AskUserQuestion の multiSelect や番号付きリスト）で示す。

### 変更してよい範囲・手を出さない範囲

- 変更するのは**モデル起因の挙動変化に関係する記述のみ**。狭く編集する
- 社内独自の用語、業務ドメイン固有の指示、ワークフローの設計判断には手を出さない
- 判断がつかない箇所は変更せず「要対応事項」に回す
- 各編集は元ファイルの文体・言語（日本語/英語）・構造を維持する

## ステップ6: 最終チェックリスト

完了時に必ず次の形式でまとめる:

```markdown
## prompt-migrate 結果

対象モデル: <モデル名> / 参照ドキュメント: <取得したページと取得日>

### 自動反映した項目
- <ファイル>: <変更内容> （[BP] or [MODEL] / 根拠）

### 人手での確認・判断が必要な項目
- <ファイル>: <要対応事項と推奨アクション>

### 変更不要と判断したファイル
- <ファイル>: <理由>
```

## 注意事項

- このスキルの守備範囲は**プロンプト（自然言語の指示）**。モデルID文字列の更新や API コード（`thinking` パラメータ、`temperature` 削除等）が見つかった場合は要対応事項として報告し、claude-api スキルの `migrate` を案内する
- ドキュメントの取得に失敗した場合は、その旨を明示した上でユーザーに続行可否を確認する。古い記憶に基づく「たぶんこうだったはず」での編集はしない
- 2回目以降の実行で差分がない場合は「変更不要」と正直に報告する。無理に指摘を作らない
