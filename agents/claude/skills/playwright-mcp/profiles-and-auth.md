# Profiles & Authentication

Playwright MCP はデフォルトで **永続プロファイル** を使う。つまり普通のブラウザと同じく、ログイン状態・Cookie・localStorage がセッション間で保持される。探索的に触る上で便利な反面、注意が要る。

## プロファイルモード

起動時の引数で切り替わる(`.mcp.json` や `claude mcp add` の args に渡す):

- **デフォルト(永続)**: ログイン状態が残る。ローカル開発の日常使いはこれで良い。プロファイルは OS のキャッシュディレクトリ配下の `ms-playwright/mcp-{channel}-profile` に保存される。`--user-data-dir=/path` で任意に指定可。
- **`--isolated`**: 毎回クリーンな状態で起動。本番や機微な環境で触る時・副作用を残したくない時・再現性が欲しい時に使う。初期状態は `--storage-state=/path/to/state.json` で注入できる。
- **`--extension`**: Playwright MCP Bridge 拡張を入れたユーザー自身のブラウザに接続する。既にログイン済みのセッションをそのまま使えるが、**ユーザーの実環境を触る** のでリスクも最大。対象タブを明示してもらってから操作すること。

## 認証済みの状態で操作したい場合の選択肢

ログインが必要なアプリを探索するときの選び方:

1. **対話的にログインしてもらう** — 永続プロファイルで `browser_navigate` → ログイン画面を表示 → ユーザーに手で認証してもらう → 以降 Claude が探索。初回だけの手間で済む。パスワードを Claude が扱わなくてよい。**第一選択。**
2. **事前保存した storageState を使う** — CI 的に動かしたいときや再現性が欲しいとき。ユーザーが `--isolated --storage-state=auth.json` で起動し、Claude は素直に使う。
3. **ユーザーが既にログイン済みのブラウザに拡張経由で繋ぐ(`--extension`)** — 手間ゼロだが本番タブを誤って触るリスクがある。対象 URL / ドメインを必ず確認してから。

**Claude が自分でパスワードをフォーム送信するのは避ける**。ユーザーが明示的にそれを望んで資格情報を提示した場合のみ行う。

## 対象が本番環境のとき

本番アプリを探索する場合、以下を一度確認:

- 読み取り専用の観察にとどめるのか、フォーム送信・決済・投稿などの副作用ある操作も許可するのか
- 許可される場合でも、destructive(削除系)は個別に確認を取る
- staging / dev 環境があるならそちらでの再現を先に提案

`--allowed-origins` / `--blocked-origins` で MCP サーバー側のアクセス範囲を制限できる。機微な環境では併用するよう提案してよい(ただしセキュリティバウンダリではない、という公式注記あり)。

## セッションを明示的にリセットしたい

永続プロファイルで作業していて「クリーンな状態から試したい」となったら:

- ユーザーに `--user-data-dir` 配下のフォルダを消してもらう、または
- MCP サーバーを `--isolated` モードで再起動してもらう

Claude 側からファイルを消しに行く必要はなく、ユーザーに操作してもらうのが安全。
